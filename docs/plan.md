# 方案：让 AI 玩《FINAL FANTASY RESONANCE》

本文是项目的总方案。第 1 节是已知情况，第 2 节是从姊妹项目带过来的原则，第 3 节是分阶段的计划，第 4 节是要用户拍板的事，第 5 节是风险。随探路结果更新。

## 1. 已知情况

- Steam 版，2026-10 发售，单机离线，没有反作弊；有 Denuvo 防篡改。
- 引擎是 Unreal Engine 5.6，资源打包是 IoStore（`.pak/.ucas/.utoc`）。游戏自己的 C++ 模块名为 `mucha`，能看到 `CPP_MuchaGameModeBase`、`CPP_MuchaGameInstance`、`CPP_MuchaWorldSetting`、`CPP_InputRegistrant`、`CPP_TitleController` 等类。GameState 用的是引擎默认类。
- 第一次探针（2026-11-22）：
  - UE4SS 正式版 v4.0.0（`EngineVersionOverride` 设 5.6）能正常注入：找到 GUObjectArray 和 FName，钩子装好，Denuvo 没有拦截，没有崩溃。
  - 只读的 Lua 探针能读到当前 World、PlayerController、Pawn、GameMode/GameInstance 的类，以及换图时的 Actor 类列表。
  - 启动流程：先进启动通知图，约 100 秒后进标题图。
- 社区已有大量 UE4SS 模组，说明这条路是通的。
- 资源包（2026-11-24 查看）：IoStore 和旧式 `.pak` 都**没有加密**，压缩用 Oodle。不用解压就能读到目录：`Content/Datatable/` 下约 2600 个数据表，按事件（分章节的对话）、地图、遇敌、角色、技能、道具、剧情标志（分章节）、章节和主线剧情、商店、任务分目录。

还不知道的（第 3 节逐项去查）：队伍、战斗、菜单、地图、存档分别在哪些类和属性里；输入走的是 Enhanced Input 的哪一层；移动是格子还是连续坐标；存档怎么分槽位。

## 2. 带过来的原则

姊妹项目 Final-Fantasy-Pixel-Remaster 花了一个多月才找到下面这些做法，这里从第一天起照做：

1. **AI 规划，代码执行。** 模型一次读一整章的事实和攻略，写出整章计划；执行器不调用模型，遇到阻塞就停下等修复，修好后从原处接着跑。
2. **计划只引用游戏数据里的编号**（事件、宝箱、出口、首领组），不写坐标和名字。提交前用数据检查：编号存不存在、走不走得到、前置剧情齐不齐。
3. **先离线、后真机。** 真机上“发现问题、修、再验证”的循环太慢。凡是能用游戏数据离线判断的，都不留到真机上才发现。
4. **只读加按键。** 桥只读游戏状态，唯一的写操作是模拟按键；不改游戏数据、内存里的数值和存档。
5. **证据说话。** 每个动作做完，用游戏状态的变化证明它确实做成了；读不到就照实报“不知道”，不猜。
6. **分层**：数据 ← 接口（真机/离线）← 执行原语 ← 章执行器 ← 规划 ← 外壳（dsh 插件、命令行），由 lint 规则管依赖方向。

## 3. 分阶段计划

每个阶段的结论写回本文。“需要游戏机”的阶段，要等游戏电脑能连上时才能做。

| 阶段 | 内容 | 需要游戏机 | 验收 |
| --- | --- | --- | --- |
| **R0 骨架** | TS 包（strict、eslint 分层、prettier、`node --test`）；`mod/` 放 UE4SS 模组；`machine/` 放游戏机端脚本（装卸模组、启动游戏、取日志），沿用姊妹项目的 SSH 和计划任务做法 | 否 | `npm run check` 通过；模组能用脚本装上、卸掉 |
| **R1 只读探查** | 用转储模组 `FfrDump`（约定见 `docs/r1-dump.md`），在标题、野外、对话、战斗、菜单、存档几个场面各取一份场面快照，外加一次对象表、反射数据（`.jmap`）、映射文件（`.usmap`）；找出队伍、敌人、回合、菜单光标、地图和坐标、剧情进度所在的类和属性。转储只放本地 `.deps/` | 是 | 一份“状态地图”：每种信息在哪个类、哪个属性，读法写清 |
| **R2 游戏数据导出** | 从 IoStore 解出数据表（角色、技能、道具、敌人、地图、任务、商店），导出成 JSON 放 `.deps/`；建数据层和查询。UE5 打包的资源一般不带属性类型，解析要用 R1 在运行时导出的 `.usmap`；工具用 C# 的 CUE4Parse（`tools/ffr-export/`），Oodle 用它自带的开源解码器，不下载专有库 | 拷一次安装目录，加 R1 的 `.usmap` | 导出可复现；关键表与游戏内显示核对一致 |
| **R3 读状态的桥** | 先做最简单的：UE4SS Lua 模组在游戏线程定时把状态写成 JSON，开发机经 SSH 读取。状态稳定后，再决定要不要做 C++ 模组提供局域网接口（见第 4 节）。已改为文件桥，见 `docs/bridge.md`。 | 是 | 开发机能稳定读到队伍、位置、场面、对话、战斗状态 |
| **R4 输入** | 在进程内注入输入（Enhanced Input），不在游戏机上装虚拟手柄驱动；游戏在后台、最小化时也能按 | 是 | 开发机发出的按键在游戏里生效，用户的键盘鼠标不受影响 |
| **R5 执行原语** | 移动、对话推进、调查、菜单、商店、存档、战斗（按规则表）逐个在真机上打通，每个都有状态证据 | 是 | 每个原语在真机上有一次成功记录 |
| **R6 离线环境** | 按 R2 的数据和 R1 的状态模型，做一个够用的假游戏，用来预跑章计划。地图如果是连续坐标，先只做“能不能从 A 到 B”的连通判断 | 否 | 第 1 章计划能在离线环境里跑完 |
| **R7 规划和章执行器** | 沿用姊妹项目的章计划、提交关口（数据检查加离线预跑）、章执行器、dsh 插件 | 否 | DeepSeek 离线写出第 1 章计划并通过预跑；真机跑完第 1 章 |

R0 不依赖游戏机。R2 的解包工具可以先做，但真正解析数据表要等 R1 拿到 `.usmap`。R1 是其余所有阶段的前提，游戏机能连上时优先做，并且一次上机就把 `.usmap` 一起取回。

## 4. 要用户拍板的事

1. **桥的形态**（R3 之后再定）：
   - Lua 模组写文件、开发机经 SSH 读：最简单，延迟大约 1 秒，回合制够用；
   - C++ 模组开局域网接口：延迟低，和姊妹项目的桥一样好用，但要在 Windows 上用 MSVC 编译，开发机上编不了。
2. **存档槽位**：照姊妹项目的规矩，只用一个固定的空槽位，不读写用户自己的存档。具体用哪个槽，等 R1 看清存档系统再定。
3. **UE4SS 常驻**：探针阶段 UE4SS 一直装在游戏目录里，每次启动游戏都会加载。用户自己正常游玩时如果不想加载，可以用 `machine/` 的脚本一键卸掉、再装回。

## 5. 风险

- **游戏更新**：版本更新可能让 UE4SS 找不到引擎结构，或者改掉我们依赖的类和属性。所以要记录探查时的游戏版本（buildid），每次启动核对；版本变了就先跑一遍只读探查再执行。
- **Denuvo**：注入太多钩子可能触发防篡改或影响性能。只装必要的钩子，读状态尽量在游戏线程里定时读，不改函数。
- **连续坐标的移动**：如果地图不是格子，寻路要靠导航网格或碰撞数据，比姊妹项目难得多。R1 先确认移动的形态。
- **战斗系统未知**：要先在 R1、R5 里看清战斗的回合、行动和目标选择，再设计规则表。
